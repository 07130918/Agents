# Codex グローバル設定

全プロジェクトに適用される Codex の共通指示。

## 言語

IMPORTANT: 英語で思考し、日本語で出力する。コード内コメント/ドキュメントはプロジェクト規約と周辺ファイルの言語を優先し、規約がない場合は日本語で書く。

成果物もすべて日本語で書く: コミットメッセージ、PR タイトル/本文、GitHub issue、レビューコメント、ログ出力、テストの説明文。

## Python 実行環境

IMPORTANT: Python 実行は常に `uv` を使う。

- ✅ `uv run python <script>` / `uv run pytest` / `uv run python -m flask run`
- ✅ `uv pip install <pkg>`
- ❌ `python3` / `python` / 素の `pip install`

## コーディング規約

### 絵文字
ドキュメント・コード内で使う絵文字は次の3種のみ:

- ✅ 成功・推奨・メリット
- ⚠️ 警告・注意
- ❌ エラー・非推奨

### 文字種
全角カッコ(U+FF08/U+FF09)は使わない。半角カッコ `()` で統一する。

### 型安全
- ❌ TypeScript の `any`。ジェネリクスや明示的な型定義で解決する。Python は型ヒントを付ける
- ✅ `let` より `const` + 宣言的な書き方を優先し、ネストした三項演算子は if 文に書き直す

## 作業の進め方

- 着手前に計画を立て、スコープを宣言する。依頼と無関係な変更 (依存更新・別ファイルの整形など) を差分に混ぜない。必要なら別 PR / issue を提案する
- ゴールに対する最小実装を優先する。過剰な防御コード・不要な抽象化・使われないヘルパーを作らない
- 機能実装・バグ修正には単体テストをセットで追加する
- 外部ライブラリの API に自信がない時は最新ドキュメントを確認してから書く (context7 など)
- 実装後は抜け穴を探すセルフレビューを行い、確信が持てるまで修正を反復してから完了報告する
- バグ修正・UI 変更は実環境で証拠ベースの動作確認 (ローカル起動 + ブラウザ/E2E/ログ) をしてから完了と報告する。自分で確認できない場合は、ユーザーが確認すべき手順を列挙して渡す
- 実装変更時は関連ドキュメント (README / docs / CLAUDE.md / AGENTS.md) との乖離を確認し、必要なら同時に更新する
- プロジェクトの CLAUDE.md と AGENTS.md は対称管理する。どちらか一方を更新したら、もう片方にも同じ変更を反映する (ラッパー化・import 化はしない)
- 自信のない判断には確信度 (高/中/低) を付け、中/低なら進む前に確認する
- 残タスク・派生問題は勝手に対応を広げず、日本語で GitHub issue 化を提案する
- 無言のログ/エラー貼り付けは「これを見て対応して」の意味。全文を読んでから対応する。明らかなタイポは意図を汲んで進め、解釈を一言添える
- ユーザーの「コミットしました」「mergeしました」「続けて」は続行合図。再確認せず次のステップへ進む
- ユーザー側の操作 (merge・認証・手動実行など) が必要な時は、待たずに具体的な依頼を 1 行で伝える

### 完了報告の形式

作業の完了報告には毎回以下を含める:

1. やったこと (1〜3 行)
2. 成果物リンク (PR / issue / コミットなど、あれば)
3. 検証結果 (lint / format / 型チェック / テストの実行結果)
4. 次にやるべきことの候補

## コードレビュー順序

中規模以上の変更・重要変更・PR 前は `/codex-review` → `/popr` の順で実行する。

## Git 運用

- main / develop では作業しない。着手前に作業ブランチを切る。issue 対応ブランチは `<issue番号>/` プレフィックス (例: `1378/fix-login-redirect`)
- コミットは既定ではユーザーが行う。エージェントは「コミット可能な状態」で停止し、対象ファイルとメッセージ案を提示する
- コミットまで明示的に任された場合 (PR 作成依頼を含む) は、意味のあるまとまりごとに分割コミットする:
  - 関数・helper・共通処理を作った単位
  - API・データ取得・永続化など処理の流れを作った単位
  - UI コンポーネント・画面表示を作った単位
  - テスト追加・テスト修正の単位
  - リファクタ・不要コード削除・設定変更の単位
- コミット前には対象ファイルを明示的に `git add <path>` でステージし、ユーザーや他作業の無関係な変更を巻き込まない。各コミットは可能な範囲でフォーマット・型チェック・関連テストが通る状態にする
- merge はユーザーが行う。エージェントは merge 品質 (可否 + 残リスク) を報告する
- ユーザーの「mergeしました」の後はベースブランチを pull し、マージ済み作業ブランチをローカル/リモートともに削除する

## コミットメッセージ

IMPORTANT: コミットメッセージは「プレフィックス + 日本語」形式で書く。

形式: `<prefix>: <日本語の要約>`

- `feat:` 新機能の追加
- `fix:` バグ修正
- `chore:` ビルド・依存関係・設定など雑務
- `refactor:` 挙動を変えないリファクタリング
- `perf:` パフォーマンス改善
- `docs:` ドキュメントのみの変更
- `test:` テストの追加・修正
- `style:` フォーマット・空白など (挙動に影響しない)
- `build:` ビルドシステム・依存関係の変更
- `ci:` CI 設定の変更
- `revert:` 以前のコミットの取り消し

ルール:
- 件名は 50 文字程度を目安に簡潔に書く (本文で詳細補足は OK)
- 「何を」「なぜ」が分かる動詞 + 目的語を心がける (例: 「修正」「追加」「更新」「削除」)
- 末尾の句点は付けない
- 英語のみ・プレフィックス無しのメッセージは作らない

## GitHub PR

- PR 提出前に lint / format / 型チェック / 単体テストを必ず通し、結果を PR 本文の動作確認欄に書く。ローカルで確認できない場合は理由と代替確認内容を明記する
- PR は宣言したスコープのみ。差分が大きくなったら分割を提案する。実装を更新したら PR タイトル/本文も差分の実態に同期させる
- PR 作成時は必ず `07130918` を assignee に設定する
- 変更内容に応じてラベルを付与する。例: リファクタは `refactor`、バグ修正は `bug`、機能追加は `enhancement`
- bot レビュー (Copilot / Gemini / Claude / Codex) はまず妥当性を検証し、正しい指摘のみ修正して PR 本文・トップコメントを同期する。誤指摘は理由を付けて返信する
- Copilot へのレビュー依頼は Codex からは行わない (リポジトリごとに統合アプリが異なるため)。必要な場合はユーザーが手動で行う

## バグ調査

- 修正前に根本原因を特定する(計画フェーズを省略しない)。症状ではなく原因を直す
- 最初に疑うパターン:
  1. 環境変数の未設定/誤設定
  2. Chakra UI v3 prop 変更の適用漏れ
  3. SQL のカンマ漏れ・NULL 扱いのミス
  4. キャッシュ不整合 (Next.js `.next`)
- 深掘りが必要なら `bug-investigator` エージェントを使う

## DB 変更

- ✅ マイグレーションファイルを必ず作成する
- ❌ 直接 `ALTER TABLE` を本番 DB に実行しない
- ✅ 相関サブクエリより JOIN を優先する (Cartesian 積・N+1 回避)
- ✅ `NOT NULL` カラムには必ず `defaultTo()` を設定する
