# レビュー・修正ハーネスの設計

## 今回の決定

契約3.0.0は、既存のpersonal skillを短い進行手順へ変更する。初回実装、文書同期、提出は既存workflowへ任せ、必要な修正と独立確認をつなぐ。新規作業に旧JSON台帳・状態遷移・自己設定上限を要求しない。

根拠は[#47の評価](https://github.com/07130918/Agents/issues/47#issuecomment-5863687676)と[ユーザーとの設計合意](https://github.com/07130918/Agents/issues/47#issuecomment-5867171080)。実装は#65、確認記録の最小仕様は[#61の合意](https://github.com/07130918/Agents/issues/61#issuecomment-5867189467)に対応する。

旧評価で有効な問題が発見されたことと、専用ハーネスの追加効果が実証されたことは異なる。軽量版の品質・完遂性・負担は未確定であり、#64の実施時期は完成後にユーザーと決める。実装に必要な検証と独立レビューは#65に含める。

## 軽量化で変えること

| 観測した問題 | 採用する対処 | 確認方法 |
| --- | --- | --- |
| P1: 診断で対象外の秘密情報が混入 | 対象と必要な取得項目に限定する | 手順の監査。実際の秘密値は使わない |
| P1: 初回実装の委譲漏れ | issue-to-prが実装済み候補を渡す | 新規Issueから提出までの接続確認 |
| P2: 修正・同原因回数と自己設定上限による停止 | 明示上限と根拠に基づく停止だけを残す | 再現試験、実装修正、小さな修正を続ける例 |
| P2: 継続・commitのたびの全面やり直し | 変更影響による結果の再利用 | 内容不変と変更ありの両例 |
| P2: 期限の説明不一致と中断後の確認漏れ | 明示期限の意味と操作前確認を共通手順へ集約する | 期限前後・中断後の例 |
| P2: 台帳の保証の過大表現 | 検出範囲と限界を明記する | 末尾削除や再ハッシュが検出できない試験 |
| P2: 除外path、型不正、終端runへの続行案内 | check-targetを廃止し、読取検証の案内を訂正する | 廃止CLIが書き込まない試験と旧記録の検証 |

対象照合コマンドの除外path・型不正の問題は、当該機能の廃止で対処する。修正済みと数えない。旧記録のpayloadを意味的に再判定する機能は追加しない。

## 残す保証と失う保証

残すもの:

- 受入条件とプロジェクトの必須確認。
- 対象コードと結果の対応、変更による結果の失効。
- 実装に参加していない担当の最終レビュー。
- 明示された制限、外部操作の権限境界、必要な停止。
- 成功・失敗・未検証の記録と、再開に必要な差分・証跡の保全。

失うもの:

- 未指定でも固定時刻・固定回数で打ち切る制御。
- 全案件での独立した初回・最終2回のレビュー。
- 全工程のJSON形式による履歴と、新規対象への専用照合コマンド。
- 同じ検証を毎回一式再実行して偶発的な問題を拾う追加の機会。

記録整合性は、バックアップや完全な改変検知、受入条件の正しさを保証しない。旧validatorの説明を訂正しても、従来から実装されていた保証が減るわけではない。

## #47の残条件と着手根拠

2026-09-28の照合では、2リポジトリ・3runのモデル情報と契約2.0.0の対応、2組の同一開始対象A/Bが確認された。通常修正による後日の完遂は、旧ハーネスの完遂へ加算しない。担当・実行条件の完全な対応表や通常工程に適合した再開などの未確認事項、未計測のtoken・費用は残る。

ユーザーはこれらを含む評価を確認して軽量化を選び、#65の実装からPR提出までを明示的に依頼した。これを今回の着手根拠とする。#47をcloseせず、未達を充足・免除に書き換えない。件数合わせの実験を追加しない。

## 切替と保全

同じPRで本体と#61の記録仕様を接続し、必須検証・独立レビューの後にローカル設定を切り替える。旧記録は[移行手順](../../../shared/references/review-harness-archive.md#移行するとき)に従って移動する。

旧契約2.1.0と旧ツール1.1.0の参照元はGit commit `2766d4aa35acb1436f09f7a22415038ff75a663f`。旧記録のschemaは1.0のまま保存する。過去記録へ現在の契約を適用して成功・失敗を再判定しない。

ローカルへの反映は今回変更したファイルに限定し、他の設定変更を上書きしない。共通referenceから参照するファイルとwrapper・toolの対応を確認し、Claude Codeの無効化状態は維持する。新しい記録が使えない状態で旧運用だけを片付けない。

## 実装時の確認と運用再評価

実装では残すコードの回帰試験、CLIの廃止経路、記録とworkflowの接続、移動前後の内容一致を確認する。手順の机上確認を実案件での完遂実績とは呼ばない。

#64では、必要に応じて実運用の品質・完遂性・記録負担を観測する。実施時期、案件、追加実験の必要性は完成時に決める。#60のmerge後連鎖、新しいrunner・fixture基盤・汎用拡張機構は今回含めない。
