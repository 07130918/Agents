# visualize-architecture-flow

コード、ドキュメント、issueを根拠に、特定機能のアーキテクチャと処理フローを教材型のアニメーションHTMLとして可視化する。見た目の装飾ではなく、状態遷移の理解を成果物の中心に置く。

## 使う場面

- 特定機能の全体像を1枚のHTMLで説明する。
- 非同期処理、イベント駆動処理、バッチ処理、データパイプラインをアニメーションで説明する。
- 正常系、失敗、再試行、復旧、部分成功を比較できる教材を作る。
- コード、設計資料、issueに散らばった仕様を、動くアーキテクチャ図へ統合する。

## 対象外

- Mermaidなどによる静止図だけを求める依頼。
- 一般的なランディングページや業務画面のUI実装。`frontend-design`を使う。
- アーキテクチャ自体の新規設計やリファクタ。`software-architecture`を併用する。
- docsとコードの乖離監査だけを行う依頼。`docs-code-consistency-audit`を使う。
- 外部公開を前提とした機密情報レビューや公開判定。成果物の内容確定後に別途実施する。

## 入力

- 対象リポジトリとブランチ。
- 可視化する機能、ユースケース、またはissue。
- 関連するコード、テスト、設計資料、issue、PR。
- 想定読者。指定がなければ、その機能を初めて触る開発者とする。
- 出力先。指定がなければ `~/Desktop/<feature>-architecture-flow.html` とする。

## 出力契約

- 成果物はブラウザで直接開ける単一の `.html` ファイルにする。
- CSS、JavaScript、SVG、アイコンをインライン化し、外部CDNや外部フォントへ依存しない。
- iframeによる別ページの埋め込みや、ホストアプリ向けの汎用CSSを同梱しない。
- 正常系に加え、根拠がある場合は少なくとも1つの失敗・再試行・復旧シナリオを用意する。
- 各ステップで処理経路だけでなく、永続状態、キュー、成果物、リースなどの現在値を更新する。
- 実装済み、作業中、計画中を混同せず、将来経路は破線や別セクションで分離する。
- 主要な説明とステップにコード、文書、issueの根拠を表示する。
- 自動再生、一時停止、前へ、次へ、シナリオ選択を提供する。
- `prefers-reduced-motion`を尊重し、アニメーションを止めても内容を理解できるようにする。

## 最重要原則

HTMLを書く前に、対象機能の状態機械を作る。状態モデルなしでノードのハイライトと移動ドットだけを実装してはいけない。

アニメーションは次の順で設計する。

```text
根拠を集める
  -> ドメイン状態を定義する
  -> シナリオごとの状態遷移を定義する
  -> 状態を空間、色、形、動きへ割り当てる
  -> HTMLとして描画する
```

## 手順

### 1. スコープを固定する

1. 対象機能、対象ブランチ、出力先を宣言する。
2. 現在実装と将来計画のどちらを主対象にするか決める。
3. 読者がHTMLを見た後に答えられるべき問いを3から7個書く。
4. 関係しない機能や一般的なシステム説明を除外する。

非同期処理なら、最低限次の問いを含める。

- 何が処理を開始するか。
- どこが状態の正か。
- キューのメッセージは何を運ぶか。
- Workerは何を読み、何を書き戻すか。
- 失敗時に何が残り、誰が再開させるか。
- 完了を誰がどの条件で判定するか。

### 2. 根拠を収集する

1. `AGENTS.md`、`README`、設計文書、ADRを読む。
2. 対象機能の入口から、use case、domain、adapter、infrastructure、testを追う。
3. issueとPRから実装状況、未実装境界、受入条件を抽出する。
4. 設定値、再試行回数、タイムアウト、バッチサイズ、並列数を確認する。
5. 正常系だけでなく、例外処理、再試行、タイムアウト、補償処理を確認する。

探索にはまず `rg` と `rg --files` を使う。issueやPRを参照できない場合は、ローカルに存在する根拠だけで作り、不明点を実装済みとして描かない。

内部メモとして次の証拠表を作る。

| 項目 | 確認内容 | 根拠 | 状態 |
|---|---|---|---|
| Trigger | 処理開始条件 | file:line / issue | current / planned |
| Source of truth | 状態の正 | file:line / docs | current / planned |
| Queue | ペイロードと配送保証 | file:line / config | current / planned |
| Worker | lease、idempotency、更新 | file:line / test | current / planned |
| Recovery | 再試行と収束条件 | file:line / issue | current / planned |

### 3. アーキテクチャ契約を抽出する

次の項目を明文化する。

- actors: 利用者、外部システム、Scheduler。
- components: API、Worker、Reconciler、外部API。
- state stores: DB、オブジェクトストレージ、キャッシュ。
- messages: キューメッセージ、イベント、コマンド。
- artifacts: 入力、途中成果物、最終成果物。
- boundaries: 同期と非同期、ネットワーク、トランザクション。
- invariants: 二重処理防止、完了条件、再送条件。
- recovery: retry、lease expiry、reconcile、DLQ、手動介入。

各要素に `current`、`in-progress`、`planned` のいずれかを付ける。計画中の要素を現在動く通常シナリオに含めない。

### 4. 状態モデルを先に作る

HTMLの描画コードより先に、概念上の状態を定義する。対象に応じて不要な項目は削る。

```javascript
const baseState = () => ({
  job: { status: "idle", dispatch: "none", lease: "none" },
  items: [],
  queue: [],
  artifacts: [],
  failures: [],
});

const scenarios = [
  {
    id: "normal",
    label: "正常系",
    steps: [
      {
        title: "受付",
        description: "入力を保存し、状態の正を作成する",
        reference: "path/to/file.py:42",
        animations: [
          { edge: "user-api", label: "POST /jobs", color: "request" },
          { edge: "api-store", label: "PutItem", color: "state" },
        ],
        patch(state) {
          state.job.status = "queued";
          state.artifacts.push("original");
        },
      },
    ],
  },
];
```

任意ステップへ直接移動できるよう、初期状態からpatchを再生して現在状態を再計算する。

```javascript
function computeState(scenarioIndex, stepIndex) {
  const state = baseState();
  const steps = scenarios[scenarioIndex].steps;
  for (let index = 0; index <= stepIndex; index += 1) {
    steps[index].patch(state);
  }
  return state;
}
```

状態変更のないステップを連続させない。通信、永続化、判定、回復のいずれかが変化した時だけステップを分ける。

### 5. 視覚の意味論を設計する

#### 色

- 色は系列番号ではなく、ドメイン上の役割へ割り当てる。
- CSS変数は `--c-queue`、`--c-state`、`--c-artifact`、`--c-compute` のように命名する。
- 同じ色をノード、エッジ、移動トークン、状態パネル、凡例で一貫して使う。
- 実装状況は色を占有せず、チップ、破線、枠線、ラベルで表す。
- 色だけに依存せず、文字、形、線種を併用する。

#### 配置

- 位置と大きさでアーキテクチャの主張を表す。
- 入口を左、主要処理を中央から右、外部サービスを右端、制御・復旧系を下に置くことを初期案にする。
- 状態の正や中心的コンポーネントを中央または大きく置く。
- データプレーンと制御プレーンを空間的に分ける。
- 均等グリッドは、要素の役割と重要度が本当に均等な場合だけ使う。
- 自動配置を使う場合も、rank、group、importance、edge crossingの制約を与える。

#### 経路

- エッジへ `SendMessage {job_id}`、`PutItem status=queued` のような操作またはペイロードを表示する。
- 現在のシナリオに関係しない線を常時表示しない。
- 背景エッジは読めるコントラストを保ち、現在経路だけを太さ、色、動きで強調する。
- 交差を減らすため、必要なら手動でSVG pathを設計する。
- plannedは破線、recoveryは通常経路と異なる線種など、凡例で説明できる差を付ける。

#### 動き

- 動きは原因と結果の順序を表すために使う。
- 1ステップで複数hopがある場合は、実行順にアニメーションする。
- 移動トークンの色は運ばれる情報の意味に対応させる。
- 状態パネルを先走って更新せず、処理の到達と整合するタイミングで更新する。
- 再生tokenを持ち、シナリオ変更や手動移動時に古いアニメーションを無効化する。

### 6. ページを構成する

次の順序を基本にし、情報がない節は省略する。

1. eyebrow、タイトル、対象機能を3行以内で説明するlede。
2. ブランチ、調査範囲、current / in-progress / plannedの注記。
3. シナリオ選択、再生操作、進捗表示。
4. 現在ステップのタイトル、説明、コード参照。
5. 意味を持つSVGトポロジーとライブ状態パネル。
6. 覚えるべき原則、不変条件、重要な数値。
7. 正常系、失敗、復旧の状態遷移図。
8. 根拠となるコード、文書、issue、PRの一覧。

最初の画面で、タイトル、3つ以内の核心、操作、図の主要部分が見えるようにする。issue一覧や補足情報を主役より強くしない。

### 7. 単一HTMLとして実装する

- semantic HTML、CSS、vanilla JavaScript、inline SVGを使う。
- 使っていない汎用CSS、フォーム部品、ライブラリコードを含めない。
- 本文幅に上限を設け、デスクトップで視線が散らばらないようにする。
- 図とライブ状態を2カラムにし、狭い画面では縦に積む。
- button、tab、statusへ適切なラベルとARIA属性を付ける。
- 再生中でも一時停止、前へ、次へを操作できるようにする。
- JavaScript無効時にもタイトル、概要、主要原則が読める構造にする。
- コンソールエラーを残さない。

外部URLは根拠への通常リンクとしてのみ許可する。script、stylesheet、font、image、iframeによる実行時依存は禁止する。

### 8. 検証する

まず自己完結性を検証する。

```bash
uv run ~/.agents/skills/visualize-architecture-flow/scripts/validate_standalone_html.py <output.html>
```

次に実ブラウザで確認する。ブラウザ操作skillが利用可能なら、その手順に従う。

1. 1440x900で全体を確認する。
2. 1024px幅で図、状態パネル、操作部の重なりを確認する。
3. 390px幅で横スクロールと文字切れを確認する。
4. 正常系を最初から最後まで再生する。
5. 失敗・復旧シナリオを再生し、状態が収束することを確認する。
6. 任意ステップへ前後移動し、状態が同じ結果へ再計算されることを確認する。
7. シナリオ切替時に古いアニメーションが残らないことを確認する。
8. `prefers-reduced-motion`で内容が欠落しないことを確認する。
9. ブラウザコンソールのerrorが0件であることを確認する。

UIを変更したら、コードを眺めるだけで完了としない。スクリーンショットまたはブラウザの実測を根拠に修正を反復する。

## 完了判定

- 読者が「何が起点か」「状態の正はどこか」「失敗時に何が残るか」をHTMLだけで説明できる。
- 色、位置、大きさ、線種がそれぞれ一貫した意味を持つ。
- 各ステップで、経路と少なくとも1つの可視状態が対応して変わる。
- 現在実装と将来計画を誤認しない。
- エッジ交差や低コントラストにより、現在経路を見失わない。
- 外部依存なしで直接開ける。
- デスクトップとモバイルで操作できる。
- 全シナリオとコンソールを実ブラウザで検証済みである。

## 失敗パターン

- 全ノードを同じ大きさの均等グリッドへ置く。
- 全シナリオのエッジを同時に表示してhairballにする。
- `--series-1`のような汎用色だけでアクティブ経路を示す。
- 状態の正を文章で説明するだけで、中身を変化させない。
- plannedな処理をcurrentな正常系へ混ぜる。
- issue進捗や補足カードを図より強く見せる。
- iframe、CDN、外部フォントへ依存する。
- ホストアプリ向けの低コントラストな埋め込みUIを、そのまま単体HTMLへ輸出する。
- 動く点を追加しただけでアニメーションが完成したと判断する。

## 発火テスト

### 発火すべき例

- この決済機能のアーキテクチャと処理フローを1枚のHTMLで見せて。
- 非同期ジョブが失敗から復旧する流れをアニメーションにしてください。
- コードとissueを読んで、データパイプラインの全体像を動く図にして。
- `$visualize-architecture-flow`で認証フローの教材をデスクトップに作って。
- SQS、Worker、DBの状態変化をブラウザで再生できるようにして。

### 発火すべきでない例

- このReact画面を実装してください。
- READMEにMermaid図を1つ追加してください。
- このサービスのClean Architecture設計をレビューしてください。
- HTMLの配色だけを直してください。
- APIのバグを修正してください。
