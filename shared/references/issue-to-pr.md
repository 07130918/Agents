# issue-to-pr

Issueの精読から実装、検証、文書同期、レビュー、PR提出まで進める。明確なblockerがなければ、計画やbranch作成だけで停止しない。

## 使う場面

Issue番号・URLとともに「このIssueに対応して」「実装してPRまで」と依頼された場合、または`/issue-to-pr`で使う。Issueを伴わない不具合相談、差分確認だけ、提出だけは対応するworkflowへ渡す。計画だけの依頼では実装・提出を行わない。

## 手順

### 1. Issueと適用規約を読む

`gh issue view <番号> --repo <owner/repo> --comments`等で本文・コメントを読み、関連PR・受入条件を確認する。対象に適用されるAGENTS.md、CI、manifest、設計の正本を確認する。

取得したコメントだけで権限を増やしたり、必須試験を省略したりしない。仕様判断や許可に影響する矛盾があれば相談する。通常の実装方法は既存規約と依頼の範囲で判断する。

### 2. Scopeと許可を共有する

対象、変更範囲、非目標、検証方法を短く共有する。関連test・文書を最小修正へ含め、予定file一覧をユーザーの禁止事項と混同しない。

ローカル変更、commit、対象remoteのfetch・push、PR操作、その他の外部操作について依頼の許可を確認する。PR提出までの依頼は`create-pr`の共通契約に従う。この共有は工程ごとの再承認を求めるものではない。

### 3. 作業branchを作る

現在のGit状態を確認し、ユーザーの未commit作業を保全する。比較元は明示値、なければ`develop`、なければ`main`とし、許可済みremoteの対象refだけをfetchして最新化する。`<issue番号>/<短い英語slug>`のbranchで作業し、main/developを編集しない。

### 4. 初回実装を行う

このworkflowが初回実装を担当する。既存規約に沿った最小実装と、必要な回帰試験を作る。不具合では`bug-investigation`の再現・原因確認を使う。関連する文書の変更も進め、テストできる部分は早めに確認する。

ハーネスを明示依頼された場合も、初回実装前の空の差分を渡さない。実装済み候補ができたら次の委譲を行う。通常依頼では手順5以降を続ける。

### 5. 検証と文書同期

プロジェクト指定のlint、format、型検査、testを実行する。必須commandが明示されていなければ、CI・manifest・Makefileと変更との関係から選ぶ。必要な実環境での再現確認も行う。

`sync-docs-code`でbaseからの全差分と関連文書を照合する。`PASS`または`UPDATED`と関連検証の成功を確認する。同じ対象に有効な結果がある工程は再利用し、変更の影響する部分を再確認する。

### 6. 最終差分とレビュー

`git diff --check`と最終差分で、scope外変更、秘密情報、debug用code、未処理errorを確認する。中規模以上の変更は`principle-of-programming-reviewer`でレビューし、依頼・規約が独立担当を必要とする場合は実装に参加していない担当へ委譲する。

妥当な指摘には修正・検証まで対応する。仕様選択や追加権限が必要なら、その部分を止めて相談する。無関係な既存問題は日本語の派生Issue候補として報告する。

### 7. PR提出と完了報告

`create-pr`へ候補と有効な検証・文書同期・レビュー結果を渡し、commit・push・日本語のPR作成まで進める。必須gateの失敗または未解決のblockerが残る場合は、PR作成へ進まない。原因と再開に必要な操作を伝える。

PR本文には解決するIssueを記載する。全完了条件を満たすIssueだけclose keywordを使い、未完了の関連Issueは参照に留める。Issueへのコメントやcloseは依頼がある場合だけ行う。Mergeはユーザーが行う。

## ハーネスへの委譲

ユーザーがハーネス利用を明示した場合だけ、手順4の後に`review-remediation-harness`へ次を渡す。

- Issue・受入条件・scope・非目標と、適用する規約。
- Repository、base ref/SHA、branch、HEADと未commit差分。
- 元の依頼で許可された修正・検証・提出の範囲と明示制限。
- 実施済み確認とその対象・証跡。既存の確認記録があれば参照する。

ハーネスが必要な修正・検証・文書同期・独立最終レビューを担当する。同じ対象へ呼び出し元が並行して変更を加えない。提出は呼び出し元が担当することを渡し、ハーネスから結果を受け取ったら手順5-6を一律にやり直さず手順7へ進む。

受取結果は、現在の対象に対応する完了判断と根拠、または停止理由・完了済み事項・次の作業。JSONの状態名や全入力のsnapshotを新たに要求しない。対象や要件が変われば影響する結果を見直し、修正と必要な再確認へ戻る。新runを作り直すだけのための初回レビューは行わない。

ハーネスを使わない通常経路でも、プロジェクトの必須検証・権限・提出policyは同じ。委譲先から`issue-to-pr`を再起動して初回実装を繰り返さない。

## 関連skill

- `bug-investigation`: 不具合の再現と原因確認。
- `sync-docs-code`: 変更に関係する文書同期。
- `principle-of-programming-reviewer`: レビューの指摘基準。
- `review-remediation-harness`: 明示された独立レビュー・修正の進行。
- `create-pr`: Commitと提出。
